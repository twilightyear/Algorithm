# \[LeetCode\] 242. Valid Anagram

---

### 📌 문제 링크

[LeetCode - 242. Valid Anagram](https://leetcode.com/problems/valid-anagram/description/)

---

### ⚠️ 제약조건

-   1 <= s.length, t.length <= 5 \* 104
-   s and t consist of lowercase English letters.

---

### 🛠️ 풀이 접근 및 분석

> Given two strings s and t, return true if t is an anagram of s, and false otherwise.

-   두 문자열 **s** 와 **t** 가 주어졌을때 문자열 **t** 가 문자열 **s** 의 **anagram** 이면 **true**, 아니면 **false** 를 반환하면 되는 문제이다.
-   **Anagram** 이란 무엇인가? 쉽게 설명하자면 철자의 위치를 재배치하여 다른 단어로 바꾸는 것을 의미한다. 즉 문자열 **s** 의 알파벳을 재배치하여 문자열 **t** 를 만들 수 있는지 물어보는 문제이다.
-   **접근 1**
    -   가장 먼저 생각한 접근법은 **Sort** 이다. 파이썬의 내장 함수인 **Sort** 를 사용하면 **Tim Sort** 가 사용되어 효율적으로 정렬이 일어나며, 이후에 정렬된 단어 두개가 같은지 비교하면 문제를 해결할 수 있다고 생각했다.
    -   **Tim Sort**는 알파벳 개수 **K** 개에 대하여 최악의 경우 **O(KlogK)** 의 시간복잡도와 **O(K)**의 공간복잡도를 가진다. 여기서 두 단어에 대하여 독립적으로 발생하기 때문에 문자열 s에 대한 알파벳 길이 L 과 문자열 t 에 대한 알파벳 길이 **M** 에 대하여 결론적으로도 본 풀이는 **O((L+M)log(L+M))** 의 시간복잡도와 **O(L+M)** 의 공간복잡도를 가진다. 조금 단순화 하여 표현하자면 **O(NlogN)** 의 시간복잡도와 **O(N)** 의 공간복잡도를 가진다고 할 수 있다.
    -   하지만 다른사람들의 풀이 대비 상대적으로 아쉬운 성능을 보였다. 다른 접근 방법을 생각해볼 필요가 있었다.
-   **접근 2**
    -   공간복잡도가 최악의 경우에서 **O(N)**은 나쁘지 않다고 할 수 있지만 **O(NlogN)**의 시간복잡도는 불필요하게 높은 수치다. 정렬이 아닌 다른 방식의 접근이 필요하다.
    -   다음으로 떠오른건 **HashMap** 의 이용이다. **Dictionary** 를 활용한다면 문자열 **s** 에 대한 알파벳 길이 **L** 과 문자열 **t** 에 대한 알파벳 길이 **M** 에 대하여 한번씩 조회가 필요하다는 점과 마지막에 문자열 **s** 에 대하여 한번 다시 조회하여 값을 확인하는 과정이 필요하다는 점을 고려하면 **O(L+M)** 의 시간복잡도를 가진다는 점을 알 수 있다.
    -   이외에도 똑같은 원리로 **O(L+M)** 의 공간복잡도를 가진다.
    -   결국 똑같이 조금 단순화한 형태로 표현하면 **O(N)** 의 시간복잡도와 **O(N)** 의 공간복잡도를 가진다고 할 수 있으며, 이는 **접근 1번** 보다도 효율적인 성능을 보일 것이라는 추측을 할 수 있다. 확인해본 결과 **접근 1번** 보다 좋은 성능을 보였지만 아직까지는 다른 사람들에 비해 비효율적인 성능을 가진것을 확인할 수 있었다.
-   **접근 3**
    -   결국 **카운터** 를 직접 구현을 하여 원소 하나하나 직접 작업하는 코드를 구현하다 보니 **오버헤드** 가 발생할 수 밖에 없다. 그렇기에 비슷하지만 다른 접근이 필요할 것 같다.
    -   다른 사람들의 풀이를 참고하여 이해해보니 결국 내장 기능의 활용이라는 요소가 상대적인 성능 차이를 보였다.
    -   먼저 **set** 을 사용하여 하나의 문자열에 대하여 **중복**을 제거한 값을 만들어놓고 이 **중복**이 제거된 값에 대하여 문자열 **s** 와 **t** 를 각각 개수를 카운트 하고 비교하면 결국 **접근 2번** 과 동일한 작동 방식을 가지지만 대부분의 처리는 내장함수를 이용한 내부 **C** 기반 작동으로 비교적 효율적이고 빠르게 처리된다.
    -   문자열 **s** 에 대한 알파벳 길이 **L** 과 문자열 **t** 에 대한 알파벳 길이가 **M** 이라고 했을때 최악의 경우 문자열 **s** 의 알파벳의 종류가 전부 다르다고 하면 set 을 만들때 공간복잡도와 시간복잡도는 둘 다 **O(L)**이 된다. 이후 이 길이 **L**에 대하여 문자열 **s** 와 **t** 의 알파벳 개수를 카운트 하고 비교하는 과정에서 **L** 번 확인하고 비교하는 과정을 거치는데, 이는 동일하게 **O(L)** 의 시간복잡도를 가지게 한다.
    -   결론적으로 **O(L)** 의 시간복잡도와 **O(L)** 의 공간복잡도를 가진다고 할 수 있으며, **접근 2번** 의 **시간/공간복잡도** 와 크게 차이가 나지는 않지만 **오버헤드/내장함수** 등에 있어서 차이가 발생한다고 할 수 있겠다.

### 📝 회고 / 추후 개선점

-   어떻게 보면 매우 쉬운 문제지만 여러 접근법을 적용하여 성능을 개선해보며 많은 생각이 들게 한 문제였다.
-   본 위에서 **set** 의 길이에 대하여도 값을 지정하여 **시간/공간복잡도** 를 분석해보았을때 결국 문제의 제약조건에 의하여 결국 **set** 의 최대 길이는 정해져 있다. 영어 소문자만 적용 가능하다는 조건에서 결국 **set** 으로 만들어진 데이터의 길이는 결국 영어 소문자의 최대 길이인 **26개** 로 제한되게 되며 이것은 결국 상수 취급이 가능한 값이기에 **O(1)** 이라고 표현해도 될 것이다. 이러한 점을 적용한다면 위의 해석이 기술적으로 완벽하게 정확한 해석이라고 할 수는 없을 것이다. 이러한 점을 기억하여 추후 해석에 있어서는 보다 정확한 분석이 필요할 것이다.
